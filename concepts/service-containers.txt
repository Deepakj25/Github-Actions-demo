###### What Are Service Containers?

Service containers are Docker containers that run beside a GitHub Actions job.

They are used when a workflow needs an external dependency during CI, such as:
PostgreSQL
Redis
MySQL
MongoDB

The service container is not your application.
It is a dependency that your application or tests connect to during the workflow.


###### Use Case

When CI runs tests, those tests may need a real database.

Option 1:
Install PostgreSQL manually on the runner
configure it
start it
clean it up

Option 2:
Run PostgreSQL as a service container
GitHub starts it for the job
tests connect to it
GitHub removes it when the job finishes


###### Basic Syntax

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16

postgres
→ service name

image
→ Docker image used to start the service


###### How The Job Connects To The Service

There are two common cases.

Case 1: job runs directly on the runner

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        ports:
          - 5432:5432

When the job runs directly on the runner, map the container port to the runner.
The job connects through:
localhost:5432


Case 2: job runs inside a container

Both the job container and service container are on the same Docker network.
The job connects using the service name:
postgres:5432

Summary:
Job on runner     → localhost
Job in container  → service name


###### Environment Variables

Service containers can receive environment variables under the service definition.
These variables are used by the service when it starts.

Example:

services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: testpass
      POSTGRES_DB: appdb

Important:
Service env variables are only for the service container.
They are not automatically available to workflow steps.

If a step needs the same value, define it again at workflow, job, or step level.

Secrets can also be used:

services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_PASSWORD: ${{ secrets.POSTGRES_PASSWORD }}


###### Port Mapping

ports:
  - 5432:5432

Format:
runner-port:container-port

This maps PostgreSQL inside the container to localhost on the runner.


###### Health Check

A running container does not always mean the service is ready.

For databases, the container may start before the database accepts connections.
A health check tells GitHub Actions when the service is usable.

Example:

services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_PASSWORD: testpass
    options: >-
      --health-cmd pg_isready
      --health-interval 10s
      --health-timeout 5s
      --health-retries 5

Common for:
databases
caches
message brokers


###### Important Points

Service containers require a Linux runner with Docker available.

Works with:
ubuntu-latest

Does not work the same way with:
windows-latest
macos-latest

Service containers are cleaned up automatically after the job finishes.


###### GH-200 Key Points

1. Service containers provide dependencies for a job.
2. They are defined under jobs.<job_id>.services.
3. When the job runs on the runner, connect using localhost and mapped ports.
4. When the job runs in a container, connect using the service name.
5. Service env variables are not automatically available to workflow steps.
6. Health checks help wait until the service is ready.
7. Service containers are supported on Linux runners with Docker.
